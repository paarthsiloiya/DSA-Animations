List-Tree Correlation

A complete binary tree needs no pointers at all: stored level by level in a flat list, the positions alone encode the family relations. Node i finds its left child at 2i + 1, its right child at 2i + 2, and its parent at ⌊(i − 1) / 2⌋ — pure index arithmetic, valid in every language. This is exactly how heaps and implicit binary trees are stored.

The Same Tree, Twice

The animation draws one tree twice: on the left as nodes and edges, on the right as a row of ten slots. The tree is built level by level — root 0, then 1 and 2, then 3 and 4 under 1, then 5 and 6 under 2, then 7 and 8 under 3, and 9 under 4 — which is precisely the order the slots are filled, so tree node i lives in list slot i.

What the animation shows: after both drawings are labelled (Tree and List Representation of Tree), the walk goes node by node from i = 0 to i = 8: the tree node and its list slot light up together, the formulas 2×i + 1, 2×i + 2 and ⌊(i−1)/2⌋ are written out with their computed values, and the Left Child, Right Child and Parent slots are highlighted in the list. For example node 3: left 7, right 8, parent 1 — and node 4's right-child formula computes 10, which the animation deliberately leaves unhighlighted: the list only has 10 slots, so that child does not exist.

Worked check for i = 3 (the sample in the code): left child 2·3 + 1 = 7, right child 2·3 + 2 = 8, parent ⌊(3−1)/2⌋ = 1 — all three match the tree, and every other node obeys the same three formulas.

Why the Formulas Hold

Levels of a complete binary tree double in size: level $k$ starts at index $2^k - 1$ and holds $2^k$ nodes. A node at index i on level $k$ has its children at the next level's matching positions — indices 2i + 1 and 2i + 2 — and inverting j = 2i + 1 or j = 2i + 2 gives the parent i = (j - 1) / 2 (integer division). One multiplication and an addition replace a pointer chase.

  • Child / parent access: $O(1)$ arithmetic — faster than any pointer dereference and cache-friendlier, since neighbouring indices share memory lines.
  • Traversal: an in-order or level-order pass costs the usual $\Theta(n)$; the formulas just replace the pointer walk.
  • Height from size: a complete tree with $n$ nodes has height $\lfloor \log_2 n \rfloor$, and the list needs exactly $n$ slots for it.

List vs. Node-Based Trees — the Trade-offs

  • Space: a list of $n$ elements exactly stores the tree — no per-node pointers. A node-based binary tree spends two extra pointers per node. But the list is fixed-size: a sparse or unbalanced shape wastes slots, and node-based trees handle arbitrary shapes gracefully.
  • Insertion / deletion: growing a list-backed tree may require reallocation and copying ($\Theta(n)$ when capacity is exhausted, amortised $O(1)$ per append); node-based insertion is always one pointer write.
  • Shape freedom: the formulas only represent a tree that is complete — complete or near-complete shapes (heaps) are the sweet spot. This is why the heap pages use the list form, while the binary search tree pages use nodes.
  • Persistence: a flat list serialises trivially (write the slots in order); a node-based tree needs a pre-order walk plus child markers to be rebuilt exactly.

Must know: the parent formula uses integer division — in Python that is //, in C/C++/Java plain / on ints — and both children of index i must be bounds-checked against the list length before use, exactly as the animation shows when node 4's missing right child computes index 10.
