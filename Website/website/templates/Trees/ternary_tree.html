Ternary Tree

A ternary tree relaxes the binary rule from two to three: every node holds at most three children. The extra branching factor makes trees shallower — a complete ternary tree fits $3^k$ nodes on level $k$, compared with $2^k$ for a binary tree — which is why ternary structures appear in tries with three-way branches and in some search trees that split each comparison into less / equal / greater.

Ternary vs. Binary — the Trade-offs

  • Height: a complete ternary tree of $n$ nodes has height $\lfloor \log_3 n \rfloor$ versus $\lfloor \log_2 n \rfloor$ for binary — shallower, but each node compares against up to three children instead of two.
  • Traversal cost: every traversal still visits all $n$ nodes once — $\Theta(n)$ regardless of branching factor; only the level sizes change (the BFS queue can grow to $\Theta(n)$ faster, since a level triples rather than doubles).
  • Storage: the array form needs three index slots per node instead of two, so sparse ternary shapes waste more space — node-based ternary trees dodge that exactly like node-based binary trees do.
  • Where they earn their keep: ternary search tries (the classic TST stores one character and three less/equal/greater pointers per node), 2-3 trees behind B-tree ideas, and interpolation searches that branch three ways.

Must know: the taxonomy rule is the only difference — parent/child, sibling, leaf, subtree and depth/height all mean exactly what they mean for binary trees; "ternary" only caps the children per node at three.
