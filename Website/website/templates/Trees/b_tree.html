B-Trees

A B-Tree is a self-balancing search tree designed for data that lives on disk. Binary search trees put one key per node, so a million-key tree is ~20 levels deep — and every level is a disk seek. A B-Tree node holds up to hundreds of keys in one disk block, so one read compares against many keys at once and the tree stays only a handful of levels tall. That is why databases (indexes) and file systems (directories, ext4, NTFS, Btrfs) are built on B-Trees and their variants (B+, B*).

Structure and Properties

A B-Tree of minimum degree $t$ orders every node with three invariants (CLRS):

  • Node shape: every node holds $n$ keys and (if internal) $n+1$ children pointers. The keys within a node are sorted, and the children interleave them — child $i$ holds exactly the keys between key $i$ and key $i+1$.
  • Key count bounds: every node except the root holds between $t-1$ and $2t-1$ keys; the root may hold as few as 1. Nodes are therefore always at least half full — the space is never wasted the way a badly split BST can waste it.
  • Perfect balance: all leaves sit at the same depth. A B-Tree never becomes a chain — it only ever grows upward, one level at a time, when the root splits.

Searching is the obvious descent: binary-search the node's sorted keys, take the child whose key range covers the target, repeat. Inserting is where the structure shines: the animation below steps through it key by key with $t = 2$ (so each node holds 1 to 3 keys — small enough to watch).

Worked Example — the Animation's Own Splits

With $t=2$ each node tops out at $2t-1 = 3$ keys. Beat by beat:

  • Insert 1, 2, 3 — the root is a leaf and simply fills to [1, 2, 3]. Each landing is the sorted place step of insert_non_full.
  • Insert 4 — the root is a full leaf: a new root is created above it, the middle key 2 is promoted to the new root, and the old root splits into [1] and [3]. Key 4 then lands right: tree [2] over [1], [3, 4]. The tree has grown one level — the only way a B-Tree ever gets taller.
  • Insert 5 — plain descent to the right leaf: [3, 4, 5].
  • Insert 6 — that leaf is full, so it is split on the way down: 4 is promoted to the root ([2, 4]) and the leaf splits into [3] and [5]; 6 lands in [5, 6]. Splitting on the way down guarantees the parent always has room for the promoted key — no upward ripples, ever.
  • Insert 7 — plain descent: [5, 6, 7].
  • Insert 8 — that leaf splits, 6 is promoted to the root ([2, 4, 6], which is now itself full); 8 lands in [7, 8].
  • Insert 9 — the root is full but the target child ([7, 8]) has room, so the animation takes its optimization path: no root split, just a plain descent to [7, 8, 9].
  • Insert 10 — now the full root and the full target child force a double split: the root splits first (4 promoted to a new root [4], over [2] and [6]), then inside the descent [7, 8, 9] splits (8 promoted, making [6, 8]) and 10 lands in [9, 10].

Final tree — three levels, every leaf at the same depth:

[4]
  [2]     [6, 8]
[1] [3]    [5] [7] [9, 10]

Count the splits: five of them, and every one happened before the key landed — the B-Tree never has to repair anything after the fact.

Complexity

  • Search / Insert / Delete: $O(t \cdot \log_t n)$ — the standard CLRS bound. The height is $O(\log_t n)$ because every internal node has at least $t$ children (so the tree holds $\ge t^h$ keys at height $h$), and each level visited does $O(t)$ work: one $O(\log t)$ binary search plus $O(t)$ pointer/key bookkeeping. With $t$ in the hundreds, $\log_t n$ is tiny — the whole point of the structure.
  • Best = Worst = Average for the shape: all leaves are always at the same depth, so there is no pathological input order — sorted input builds the same tree as random input (contrast a BST, which sorted input degrades to a chain, and an AVL tree, which repairs after the fact).
  • Space: $\Theta(n)$ — every node except the root is at least half full, so the total node storage is a constant factor of the keys stored.

Must-Know Points

  • Splits happen on the way down (insert) — the parent is guaranteed to have room for the promoted key, which is why B-Tree insertion is a single top-to-bottom pass with no rebalancing on the way back up.
  • Growth is always upward — the tree gets taller only when the root itself splits; a new root of one key is created above the old one.
  • High $t$ = shallow tree — $t$ is tuned to the disk block size so one node = one block; a height-3 B-Tree with $t=256$ can index 16 billion keys.
  • Children interleave the keys — child $i$ holds exactly the keys between keys $i$ and $i{+}1$, which is what makes the descent a plain range check.

vs. BST / AVL: a B-Tree is the multiway generalization of a BST (a B-Tree with $t=2$ and 1-key nodes degenerates to one), and it shares the AVL property that all leaves are equidistant from the root — but a B-Tree maintains it by construction (split on the way down) rather than by repair (rotate after the fact). Applications: database indexes (B+Trees), file-system directories, key-value stores.
