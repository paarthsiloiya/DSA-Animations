Huffman Encoding

Huffman coding builds the most compact prefix code for a set of symbols: a binary code where no codeword is the start of another (prefix-free), so an encoded stream can be decoded on the fly with zero ambiguity. Frequent symbols get short codes, rare ones get long codes — and the assignment provably minimizes the total number of bits. It is a greedy algorithm: repeatedly merge the two least frequent symbols.

Two Smallest, Merge, Repeat

  1. Count each symbol's frequency in the input.
  2. Repeatedly merge the two least frequent items into a parent node: its frequency is their sum. Each merge draws a left edge labelled 0 and a right edge labelled 1.
  3. When one item remains, it is the root. A symbol's code is the $0/1$ path from the root down to its leaf — which is exactly why no code can prefix another: every symbol lives at a distinct leaf, and prefixes would require one leaf to sit on another's path.

What the animation shows: the demo string "abbcaaaabbcdddeee" (17 characters) with counts c: 2, d: 3, e: 3, b: 4, a: 5. Leaf circles fade in, then four merge rounds play out — each announcing "Select two nodes with smallest frequencies", the pair under consideration ("Combining c(2) + d(3)"), the parent's frequency, and the connecting edges with their $0$ (left) / $1$ (right) labels. The verified merge order:

c(2) + d(3) → cd(5)  ·  e(3) + b(4) → eb(7)  ·  a(5) + cd(5) → acd(10)  ·  eb(7) + acd(10) → root(17)

One honest note: the animation focuses on tree construction — it never displays the final binary codes for the symbols. Reading them off is a text-book exercise on the finished tree: walk from the root, appending $0$ for each left edge and $1$ for each right edge, and collect the path at each leaf. Doing that on the tree built above yields a = 10, b = 01, c = 110, d = 111, e = 00 — verified prefix-free, and decoding the 17 characters bit by bit returns the original string. The encoding weighs in at 39 bits against 51 bits for a naive fixed 3-bit code — and there is a neat identity to check any run: the total bit cost equals the sum of all merged frequencies ($5 + 7 + 10 + 17 = 39$), because a symbol's code length is exactly the number of merges its subtree passes through.

Complexity

  • Best / Worst / Average: $O(n \log n)$ over $n$ distinct symbols — the standard implementation keeps the pool in a min-heap: each of the $n - 1$ merges does two $O(\log n)$ extracts and one $O(\log n)$ insert, and the initial frequency count is a single $O(\text{len}(s))$ pass over the input. Every merge is unconditional, so no case beats the bound.
  • The re-sort variant shown here: the animation and the code re-sort the whole pool each round — simple to follow, at the cost of an extra factor (each round's sort is $O(k \log k)$ on a pool of size $k$). The classic two-queue refinement exploits the fact that merged frequencies only grow: one queue of sorted leaves plus one FIFO of merged parents makes every round $O(1)$, leaving the initial sort's $O(n \log n)$ as the whole cost.
  • Space: $O(n)$ for the tree and the pool (one leaf per distinct symbol, one internal node per merge).

Must know: Huffman coding is optimal among prefix (symbol-by-symbol) codes — every Huffman tree for the same frequencies costs the same total, though ties in the pool can produce different trees and different (equally good) code lengths; the demo breaks ties deterministically by $(\text{frequency}, \text{symbol})$ so the video is reproducible; $0$/left and $1$/right is a convention — swapping them mirrors every code; and the tree built bottom-up by merges is a full binary tree: every internal node has exactly two children.

Applications

  • File compression: DEFLATE (zip, gzip, PNG) uses Huffman coding as its final stage.
  • Media formats: JPEG and MP3 encode quantized coefficients with Huffman tables.
  • Transmission coding: compacting teletext and Morse-like protocols by symbol frequency.
  • Anywhere symbol frequencies are skewed: databases, log compression, custom archive formats.
